# Vendor Capability Research

This document captures vendor documentation signals that may inform the evolution of the Canonical Banking Capability Model (CBCM). The research is intended to identify missing or under-modeled capability areas, not to score vendors or copy vendor module boundaries into the canonical model.

## Research Intent

The primary question is:

> Which business capability areas appear across modern core banking products but are absent, thin, or modeled at the wrong level in the current CBCM?

The research should preserve vendor neutrality. A vendor term is evidence of market language; it is not automatically a canonical capability name.

## Source Rules

| Rule | Application |
|---|---|
| Prefer official public documentation | Use vendor docs, developer portals, official product pages, and open-source project docs before analyst reports or commentary. |
| Separate evidence from interpretation | Record what the source exposes, then map it to a possible CBCM implication. |
| Track confidence | Public docs vary in depth; mark findings as high, medium, or low confidence. |
| Avoid implementation overfitting | Do not add a capability only because a vendor implements it as a named product or module. |
| Preserve dated context | Public documentation changes; record access date for each research pass. |

## Gap Types

| Gap type | Meaning |
|---|---|
| New capability candidate | The current CBCM does not have an obvious owning capability. |
| Existing capability expansion | The current CBCM has an owner, but the content should be deepened. |
| Existing capability split | The current CBCM combines responsibilities that may deserve distinct ownership. |
| Evaluation dimension | The subject is important for vendor assessment but should not become a business capability. |
| Vendor-specific detail | Useful evidence, but not appropriate for CBCM structure. |

## Early Cross-Vendor Signals

| Signal | Vendors observed | CBCM interpretation |
|---|---|---|
| Cards are more than payments | Mambu, Tuum, Temenos, Thought Machine | Add Card Management / Card Servicing as a candidate business capability. |
| Credit exposure spans products | Mambu, Tuum, Temenos | Add Limits and Exposure Management as a candidate policy or risk capability. |
| Product design is operationally deep | Mambu, Tuum, Thought Machine, Temenos | Expand Product Catalog into Product Design, Product Lifecycle, Simulation, Versioning, and Product Change Control. |
| Corporate and commercial banking has distinct structures | Tuum, Temenos, Thought Machine | Add Corporate Credit Facilities and Commercial Finance candidates. |
| Payments include orchestration, routing, liquidity, and compliance | Tuum, Temenos, Mambu, Thought Machine | Refine Payment Processing into clearer sub-capabilities or feature groups. |
| Islamic finance is a recurring product-family specialization | Mambu, Tuum, Temenos, Thought Machine | Add Islamic Finance Support as a specialization, not merely an interest-rate variant. |
| Migration is a first-class transformation concern | Thought Machine, Temenos | Add Data Migration / Back-Book Migration as a platform or transformation capability candidate. |
| Regionalization and regulatory packs matter in vendor evaluation | Temenos, Mambu, Tuum | Add Regionalization / Localization as an evaluation dimension, and possibly a platform capability. |
| Real-time events and data hubs are prominent | Mambu, Thought Machine, Temenos, Fineract | Expand Integration, Reporting, and Platform Services around event streams, operational data stores, and governed data products. |
| Financial crime and onboarding are adjacent but important | Temenos, Tuum, Fineract, Mambu | Add Financial Crime Interface and Party Onboarding/KYC candidates, with careful boundary placement. |
